# HW6 Problem 4 — 有缓存 vs 无缓存的真实成本

所有数字都来自 API 实际返回的 usage，费用按 `data/prices.json` 计算。逐次调用的原始数据在 [`cache_test.json`](cache_test.json)。

- 运行时间：2026-10-13 03:36–03:50 UTC
- 模型：`gpt-6-luna`，经 Portkey 走 Responses API
- 代码：[`scripts/cache_test.py`](../scripts/cache_test.py)、[`agent.py`](../agent.py)（新增 `--cache on|off` 参数）

## 1. 两种设置怎么实现，API 数据如何证明有效

两组用的是同一个 Agent：完整手册 + 同一份 `prompts/prompt.md` + 同样 3 个工具 + 同一份文档 + 同样的结构化输出。唯一的区别是缓存设置。

### with_cache（`--cache on`）

- **做法：**
  - 固定前缀放在最前面：工具定义 + instructions（完整手册 → `---` → 任务说明）。
  - 变化的内容都放在后面：用户消息里的文档路径、工具返回的文档正文。
  - 使用默认的 implicit 缓存模式（OpenAI 自动设断点）。
  - 固定 `prompt_cache_key = "campus-customs-vendor-desk"`，让相同前缀尽量路由到同一缓存。
- **证据：** 正式 24 次调用中，有 23 次 `cached_tokens > 0`，共读取 **250,621** 个缓存 token。
  - p02–p12 的第 1 次调用各读到 10,886 个缓存 token，说明**跨文档**复用了手册前缀。
  - 每份文档的第 2 次调用（工具调用之后）读到 10,905 个缓存 token。

### without_cache（`--cache off`）

1. **先确认接口能否直接关闭缓存。** SDK 的 `prompt_cache_options` 说明写着：`mode="explicit"` 且没有显式断点时，“请求不使用提示词缓存”。
   - 我先只用这个参数做了最小验证，**结果失败**。同一次运行的第 2 次调用仍然 `cached_tokens = 10,905`。
   - 这条失败记录保留在 `cache_test.json` 里（`phase = validation`，`setup_check_passed = false`）。
   - 因为我改代码时出错，失败的验证又多跑了 1 次，结果一样，同样保留了。
   - 结论：经 Portkey 调用 gpt-6-luna 时，这个参数单独**不能**保证没有缓存读取。
2. **改用缓存绕过。** 每一次模型请求都在 instructions 最前面加一个随机 nonce（`[request nonce <uuid> - ignore]`）。
   - PydanticAI 每次请求都会重新生成 instructions，所以工具调用之后的第 2 次请求也会拿到新的 nonce。
   - 缓存只匹配“从第一个 token 开始完全相同的前缀”，开头每次都不同，后面的手册再一样也读不到缓存。
   - 手册、任务说明和文档内容都没有删减或改动，每次请求只多了约 24 个 token。
   - `mode="explicit"` 参数仍然保留。
3. **证据：** 正式 24 次调用**全部** `cached_tokens = 0`。
   - API 每次都返回了 `cached_tokens` 这个字段，所以这是实测的 0，不是缺失后被当成 0。
4. **对比较的影响：**
   - nonce 让每次请求多约 24 个 token，费用影响不到 0.3%。
   - **但它没有阻止缓存写入。** API 仍然对每次请求的几乎全部输入报告了 `cache_write_tokens`，见第 7 节。

### 验证与统计范围

- `cache_test.json` 共 **60 条调用记录**：
  - 12 条最小验证（p01，3 轮 without_cache + 3 轮 with_cache，每轮 2 次调用），**都不纳入**正式比较。
  - 48 条正式记录（12 份文档 × 2 组 × 2 次调用），**全部**通过设置检查，**全部纳入**。
- 正式运行都在第 1 次尝试成功，没有重跑，也没有筛选。
- 两组都没有调用 `send_email` / `approve_payment`，`trap_calls.json` 仍然是 `[]`。

## 5. 和第 2 题估算的比较

**token 数：**
- 第 2 题用 tiktoken `o200k_base` 统计手册是 **10,058** token。
- 探测调用（`output/cache_probe.json` 中的 F 组）只发送“手册 + `Say OK.`”，API 报告输入 10,071 token，与 tiktoken 的估算相差约 0.1%。

**费用：**
- 第 2 题**只算了手册本身的输入**：
  - 无缓存 $0.0010058 / 次
  - 全部命中缓存 $0.00010058 / 次
- 实测每份文档有 **2 次调用**，按第 2 题的口径换算：
  - 无缓存 ≈ $0.0020116 / 份
  - 全部命中 ≈ $0.00020116 / 份

| | 第 2 题口径 × 2 次调用 | 实测平均每份 | 差额来自 |
|---|---|---|---|
| 无缓存 | $0.0020116 | $0.00288125 | 缓存写入价（$0.125）高于普通输入价（$0.10）；任务说明、工具定义、文档正文（约 850 token/次）；输出 |
| 有缓存 | $0.00020116 | $0.00047597 | 第一份文档建立缓存的写入费；每次调用还会写入新尾部；原价输入；输出（约占 27%） |

实测费用里包含了手册以外的提示词、工具定义、供应商文档、输出，以及每份文档的 2 次调用。所以两者的差额**不能**全部归因于缓存，第 2 题的数字只是手册部分的下限。

|---|---|---|
| without_cache | $0.00288125 | **$86.44** |
| with_cache | $0.00047597 | **$14.28** |
| **预计节省** | | **$72.16** |

这是按 12 份样本的平均值外推的结果：
- with_cache 的平均值里，第一份文档（p01）承担了一次完整的缓存写入。实际每天 1,000 份时，这笔写入会被分摊得更薄。
  - 只用稳定状态的 p02–p12 计算，平均每份 $0.00037186，月费用约 $11.16，节省约 $75.28。
- 实际结果还受缓存有效期（默认 30 分钟）的影响：间隔超过有效期，就要重新付写入费。
- 也受请求路由、调用模式的影响，比如文档更长、或需要更多次工具调用。

## 7. 值得注意的现象

1. **“无缓存”反而比按普通输入价计费更贵。**
   - without_cache 组虽然没有读取缓存，但 API 对每次请求约 11,000 个输入 token 都报告了 `cache_write_tokens`。
   - implicit 缓存会自动把提示词写入缓存，而写入价 $0.125 / 1M 比普通输入价 $0.10 高 25%。
   - nonce 让每次前缀都不同，所以每次都要重新写、永远读不到。只付写入的溢价，拿不到折扣。
   - 如果这 267,285 个输入 token 都按普通价计费，总费用应是 $0.02797；实际是 $0.03458，**多出 23.6%**。
   - 这说明“没有复用缓存”不等于“没有缓存费用”。破坏前缀的提示词设计（例如把时间戳、请求 ID 放在最前面）会让成本比完全不缓存还高。
2. **第一次写入的成本。**
   - with_cache 组的 p01 第 1 次调用写入 10,905 token，费用 $0.00136。这使 p01 只省了 43%，其余文档都省了约 87–88%。
   - 写入后，后面 11 份文档的第 1 次调用都读到 10,886 个缓存 token，所以这笔一次性的写入费很快就被摊薄。
3. **有缓存时也会持续产生少量写入。**
   - implicit 断点在每次请求的末尾，每次调用都会把新的尾部写入缓存：第 1 次调用约 20 token（文档路径），第 2 次约 150–170 token（工具调用和文档正文）。
   - 这些写入很少，12 份文档一共 $0.0016，其中大部分还是 p01 的首次写入。
4. **多次调用会放大缓存的作用。**
   - 每份文档需要 2 次模型调用，第 2 次要重新发送整份手册和前面的对话。
   - 没有缓存时，手册在一份文档里要按写入价付 2 次；有缓存时，第 2 次几乎全部按读取价计费。
   - Agent 调用工具的次数越多，缓存省下的钱就越多。
5. **跨请求的缓存命中不能保证。**
   - 最小验证和调试时，同一份 p01 连续多次运行，第 1 次调用都没有读到缓存（每次都写入 10,905 token）。只有同一次运行的第 2 次调用稳定命中。
   - 探测调用（`output/cache_probe.json`）中，完全相同的两次请求有时命中、有时不命中。
   - 正式实验中，p02–p12 的第 1 次调用都命中了。这说明缓存是尽力而为的（与路由有关），实际节省会随流量模式波动。
6. **输出不是主要差别。** 两组的输出 token 接近（2,480 vs 2,549），费用差距几乎完全来自输入的计价方式。
